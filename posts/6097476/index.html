Claude Code 源码解析（五）：Reactive Compact 与 413 恢复

发表于 2026-07-12 更新于 2026-07-13 分类于 Agent Waline：
接续上下文预处理：API 报错后的 reactive compact 全链路——withhold、collapse drain、tryReactiveCompact、媒体恢复，以及 staged queue / commit 语义（非 Git）。

接续第四篇的 proactive 上下文预处理（budget → snip → microcompact → collapse → autocompact），本文专讲其对称另一半：reactive 恢复——当 proactive 没压住、或刻意 reactive-only 时，真实 API 返回 413 / 媒体过大后，queryLoop 如何 withhold 错误、尝试抢救、再决定 surface 或 continue。

源码说明：reactiveCompact.js、contextCollapse/index.js 等为 REACTIVE_COMPACT / CONTEXT_COLLAPSE feature-gated，外部 build 可能不存在；本文以 调用方 + 类型定义 + 共享工具 为准还原行为。

Proactive vs Reactive：同一问题的两面

Proactive（第四篇）Reactive（本篇）
触发时机调 API 之前，本地 token 估算调 API 之后，收到真实错误
典型手段snip / microcompact / collapse 投影 / autocompactcollapse drain → tryReactiveCompact
目标尽量不让请求失败请求已失败时 抢救一轮

Reactive-only 模式（GrowthBook tengu_cobalt_raccoon）：关闭 proactive autocompact，专门等 API 413 再 compact（autoCompact.ts ~195–198）。手动 /compact 在该模式下走 compactViaReactive（commands/compact/compact.ts ~87）。

413 错误如何变成一条 message

API 抛错后，getAssistantMessageFromError（errors.ts）将其规范为带 isApiErrorMessage 的 assistant message。

Prompt too long（413 / 400）

Vertex 常返回 413，直连 API 常返回 400，文案都含 prompt is too long：

判定：isPromptTooLongMessage(msg) — isApiErrorMessage 且 content 里 text 以 "Prompt is too long" 开头。

Reactive 恢复会用 getPromptTooLongTokenGap(msg) 从 errorDetails 解析 超出多少 token，以便一次丢掉足够多的 API round 组，而不是一组一组剥（errors.ts ~104–117；proactive 侧同类逻辑见 compact.ts truncateHeadForPTLRetry）。

媒体过大（image / PDF / many-image）

平行路径：isMediaSizeError / isMediaSizeErrorMessage（errors.ts ~133–152）。content 是用户可读文案；errorDetails 存原始 API 串，供 reactive 判断是否可 strip 后重试。

错误类型恢复手段
413 PTLcollapse drain → reactive compact（摘要）
媒体过大仅 reactive compact（stripImagesFromMessages 后重试）

Media error 不走 collapse drain：collapse 投影只替换 text span，不 strip image/document。

流式 Withhold：先藏起来，再决定要不要给用户看

query.ts ~788–825：API 流中收到 assistant message 时，若为 可恢复错误，则 不 yield 给 UI/SDK，但仍 push 到 assistantMessages，供后续恢复逻辑读取。

为什么要 withhold

  1. SDK / desktop：看到 error 字段可能 直接终止 session；恢复还在跑时泄露错误，调用方已退出，抢救无人接收（query.ts ~166–171 注释，与 max_output_tokens withhold 对称）。
  2. 用户体验：能恢复则不先展示失败；确认救不回来再 yield lastMessage。

mediaRecoveryEnabled 必须 hoist

mediaRecoveryEnabled 在流式 前 算一次（query.ts ~626–627），流中与流后恢复必须用 同一值。否则可能出现「流里 withhold 了、流后认为 recovery 关闭」→ message 丢失。

恢复链：只在 !needsFollowUp 时执行

needsFollowUp 是什么

needsFollowUp 不是「要不要 compact」的开关，而是 这一轮 API 响应有没有留下未完成的 tool 轨迹（query.ts ~554–558）：

每一轮 iteration 在流结束后 二选一：

needsFollowUp路径
true执行 tool → 拼 assistant + tool_results → continue（transition: next_turn）
false收尾：413 恢复 / max_output_tokens 恢复 / stop hooks / completed

413 恢复写在 if (!needsFollowUp) 里（query.ts ~1062–1183），与 stop hooks、正常结束 共用同一出口。

为什么只有 !needsFollowUp 才触发恢复

1. 413 在实践里几乎是整请求失败

prompt is too long 是请求级拒绝：返回 isApiErrorMessage，通常不含有效 tool_use。触发恢复时 needsFollowUp 自然为 false。

2. 避免在「半段 tool 轨迹」中间 compact

若 needsFollowUp === true，history 里已有 tool_use 但尚未产生 tool_result。此时 tryReactiveCompact 若把 state.messages 换成 postCompactMessages 再 continue：

  • 可能丢掉 in-flight 的 tool 流或已部分 yield 的结果
  • 破坏 tool_use ↔ tool_result 配对（API 硬要求）
  • UI 上出现「模型要了 tool → 历史突然被摘要替换」的断裂感

有 tool 要跟 → 先走完 tool 路径；compact 等这一轮 agentic step 闭合。

3. 不是永远不做 reactive，而是 defer 到合适的一轮

Tool 跑完后的 continue（query.ts ~1715–1725）会：

下一轮重新走 Phase 1 预处理，再 callModel。若仍 413 且 needsFollowUp === false，reactive 恢复才会触发。

好处归纳

好处说明
保护 tool 配对不在 tool_use 已发、tool_result 未齐时改 history
分支清晰恢复 = callModel 失败；tool 路径 = callModel 成功且要了 tool
符合 413 形态失败请求通常无 tool_use
收尾集中与 stop hooks、completed、max_output_tokens 同分支
下轮仍有机会tool 结束 → proactive 预处理 → 仍可 reactive

时间线示例

长 agentic turn：先让 tool 闭环，再在无 tool 的失败点（或下一轮）压 context。

Collapse drain 专节（非 Git 概念）

第四篇提到 context collapse 的 读时投影；本节说清楚 drain 涉及的 staged / commit 语义。

重要：下文 staged、commit、queue、drain 均不是 Git 概念，与 utils/git.ts、/commit 命令无关，只是 Context Collapse 子系统借用了相近词汇。

双状态：Staged vs Committed

状态含义持久化
Staged「这段 span 要压成摘要 S」已写好，尚未对模型视图生效内存队列 + 快照 marble-origami-snapshot
Committed已登记，投影时 span → <collapsed>摘要</collapsed>追加 marble-origami-commit

REPL messages[] 一般不删；commit 只影响 模型看到的投影视图（projectView）。

Staged queue 里有什么

types/logs.ts ContextCollapseSnapshotEntry：

谁写入 staged queue

主要是 ctx-agent（querySource === 'marble_origami'）在后台产出：

  1. 上下文涨到约 90% → 开始 commit 流程；约 95% → 可能 blocking spawn（autoCompact.ts ~201–205 注释）
  2. spawn ctx-agent，分析对话、选定 span、写好 summary
  3. 结果入 staged queue（内存）
  4. 每次 ctx-agent spawn 结束 → 快照写入 transcript（types/logs.ts ~274–275）

/context 可显示 N staged（commands/context/context-noninteractive.ts ~128）。

「积压的 collapse」

已在 staged queue 里排队、但 还没 commit 的项。ctx-agent 一次可能产出多段；正常路径未必立刻全部 commit，对话继续变长时队列会堆着多段「摘要已写好、投影未生效」的 collapse——模型视图里 原文仍在，token 未降。

Commit 做什么

  1. 追加 marble-origami-commit（span 边界 uuid + summaryContent 等）
  2. 之后 applyCollapsesIfNeeded → projectView 重放 commit log，模型视图里该 span 变为 <collapsed>
  3. 原始 user/assistant 仍在 transcript；commit 条目 不 重复存 archived 正文（types/logs.ts ~240–244）

Drain = 413 时一次性 commit 全部 staged

recoverFromOverflow(messagesForQuery, querySource)：

  • 把 staged queue 里 所有 待处理项 一次性 commit（排空队列）
  • drained.committed > 0 → 更新 state.messages，transition: 'collapse_drain_retry'，continue 重试 API
  • 只 drain 一次：若上轮已是 collapse_drain_retry 仍 413 → fall through 到 reactive compact
  • 队列空 → committed === 0，跳过 drain

相对 reactive compact，drain 便宜（摘要已写好，只 commit）；reactive compact 贵（fork 摘要 agent）。

tryReactiveCompact：最后手段

query.ts ~1119–1165：

  • 产出与 proactive 相同：buildPostCompactMessages → boundary + summary + attachments
  • 成功后 autoCompactTracking 置 undefined（当作全新 compact 后上下文）

hasAttemptedReactiveCompact：每 turn 最多一次

场景行为
首次 413，compact 成功true + continue
compact 后仍 413 / media error不再 compact，surface 错误
stop-hook blocking 后 continue不能 reset 该 flag（query.ts ~1292–1297）

否则死循环：compact → 仍太长 → error → stop hook 注入 token → 再 compact → 无限 API 调用。

恢复失败：不走 handleStopHooks

  • 不走 handleStopHooks（会注入 blockingErrors 再 continue，与 413 叠加 → error → hook → retry → error）
  • 只跑 StopFailure hooks（executeStopFailureHooks），不往 history 塞继续对话的 blocking message

与 Blocking Preempt 的配合

发 API 前 的 synthetic 413（blocking_limit，query.ts ~637–647）在以下情况 skip：

条件原因
reactive compact enabled 且 isAutoCompactEnabled()需要 真实 API 413 触发 reactive
context collapse enabled 且 isAutoCompactEnabled()同上，drain 依赖真实 413
本轮刚 autocompact 成功stale usage 会误判
snip 已 freeing token计数需减 snipTokensFreed
querySource === 'compact' | 'session_memory'fork agent 不能在此被拦死

用户设 DISABLE_AUTO_COMPACT 时 仍 可能走 blocking preempt（「不要自动 anything」优先于 reactive 路径）。

手动 /compact 的 reactive 路径

compactViaReactive（commands/compact/compact.ts ~139–227）：

  • 并发 executePreCompactHooks + getCacheSharingParams
  • 调 reactiveCompactOnPromptTooLong（内部跑 PostCompact hooks）
  • 失败 reason：too_few_groups / aborted / exhausted / media_unstrippable 等

邻接：max_output_tokens 恢复（同一 withhold 框架）

同一段 !needsFollowUp 内（query.ts ~1185–1256），与 413 共用 withhold，但 不走 compact：

  1. 默认 8k cap 命中 → 升到 ESCALATED_MAX_TOKENS（64k）同请求重试
  2. 仍不够 → 注入 meta user message「Output token limit hit…」，最多 3 次
  3. 耗尽才 yield withheld error

六个自检问题（含答案）

1. 为什么 413 在流式里不立刻显示？

可恢复错误先 withhold。SDK/desktop 见 error 可能终止 session；恢复成功则用户无需看到中间失败。确认救不回来再 yield。

2. 为什么先 collapse drain，再 reactive compact？media 为何跳过 collapse？

先便宜后昂贵：drain 用已 staged 的摘要 commit；reactive 要 fork 整段摘要。collapse 不处理 image/PDF，media 必须走 strip + reactive。

3. hasAttemptedReactiveCompact 防什么？

每 user turn 最多自动 reactive compact 一次；stop-hook 路径不得 reset，防 compact ↔ error ↔ hook 死循环。

4. 为什么 413 失败后不能走 handleStopHooks？

模型无有效回复；stop hook 会注入更多 token 再 continue，形成 error → hook → retry → error 螺旋。只跑 StopFailure hooks 并 return。

5. proactive autocompact、blocking preempt、reactive 何时互斥？

collapse on 或 reactive-only → proactive off；reactive/collapse + autocompact on → blocking preempt off（要真 413）；DISABLE_AUTO_COMPACT → blocking 仍可能拦。

6. 为什么 413 恢复只在 !needsFollowUp 时触发？

needsFollowUp 表示本轮 API 是否还有未完成的 tool（已收 tool_use、待跑 tool）。为保 tool 配对，不在半段轨迹中 compact；413 失败通常也无 tool_use。Tool 跑完后的下一轮仍可触发 reactive。

小结

  1. Reactive 是 proactive 的对称补位：前者 API 前压 context，后者 API 失败后抢救
  2. Withhold：可恢复错误先不 yield，救不了再 surface
  3. 恢复顺序：413 → collapse drain（排空 staged queue，非 Git）→ reactive compact；media 跳过 drain
  4. Staged / commit：ctx-agent 写 staged queue；commit 让投影生效；drain = 413 时批量 commit
  5. hasAttemptedReactiveCompact + 不走 stop hooks：防死循环与 token 螺旋
  6. Blocking preempt 与 reactive/collapse 配合时需 skip synthetic 413，保留真实 API 错误作触发信号
  7. !needsFollowUp：恢复只在无待执行 tool 时触发，保护 tool 轨迹；tool 结束后的下一轮仍可 reactive
