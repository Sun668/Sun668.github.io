Codex 工程实践（二）：上下文如何压缩与拼接

发表于 2026-10-25 更新于 2026-11-06 分类于 Agent Waline：
结合核心循环与 Prompt 组装，拆解历史压缩、初始上下文重注入和 Skill 按需加载，说明如何在有限窗口内保留任务状态与证据。

Coding Agent 一轮又一轮地读文件、运行工具，上下文很快会超过一开始的任务描述。真正难的地方是：空间变少以后，哪些信息还能支撑下一步决策；压缩完成以后，哪些规则需要重新组装进去。

《Codex 源码分析》第 6、7 章分别从核心循环和 Prompt 组装解释了这两个问题。把它们连起来看，上下文管理包含两项工作：维护可继续执行的历史，以及为下一次模型请求准备正确的材料。

一、上下文由哪些东西组成

把上下文理解成聊天记录，容易忽略真正占空间、也真正影响执行的部分。

内容作用管理方式
基础指令与运行约束定义行为、执行条件从可信配置和运行状态构造
项目规则与能力目录说明仓库约定、可用能力按路径发现，控制体积
当前任务和最新纠正决定这次要做什么保留明确目标与变化
工具调用及结果提供执行过程和证据保持关联，减少低价值输出
历史总结与近期交互支持跨阶段继续工作压缩旧内容，保留近期细节

这里还存在一种重要差别：有些内容可以从文件和运行状态重新取得；有些内容只存在于本次交互中，例如用户刚刚撤销了一个方案。后者在压缩时更容易丢失，也更需要被明确保存。

二、为什么压缩会出现在回合中途

第 6 章展示的核心循环是分层的：会话接收操作，任务驱动一个回合，一个回合里又会多次请求模型与执行工具。

所以，“一次用户输入”并不等于“一次模型调用”。代理在执行一个复杂任务时，可能已经读入数十份材料；即使用户没有再发消息，也可能需要在回合中途压缩。

容量预算也不能只看当前文本。下一次请求还需要容纳新工具结果、补入的上下文和输出。可以用下面这个设计关系理解：

调试自动压缩时，可以用 codex -c model_auto_compact_token_limit=12000 开一个实验会话。这个顶层配置键调整的是自动压缩触发阈值，模型窗口仍由运行时和模型能力决定。默认按当前活跃上下文计量，支持 model_auto_compact_token_limit_scope = "body_after_prefix" 的版本也可以按保留前缀之后的增长计量。12000 只是便于观察的试验值，删掉覆盖后由模型默认值决定触发点。自动压缩参数

三、压缩的对象是历史表示

我会把“压缩”分成三种处理，避免混淆。

输出裁剪处理体积。例如把很长的日志保留首尾，注明中段省略，并留下原始文件路径。这会丢掉内容，适合处理暂时不需要逐行阅读的输出。

语义摘要处理信息密度。它把多个步骤转成当前状态：已经尝试什么、验证了什么、哪些方案已废弃、接下来做什么。摘要同样可能丢信息，也可能写错。

历史替换则让后续请求使用新的历史表示。它必须保持消息结构和上下文边界，不能只把一段摘要随意追加到原始历史末尾。

以本地压缩路径为例，运行时用现有历史发起摘要请求，从模型响应取摘要，再用选出的用户消息与摘要重建历史。回合中途压缩时，运行时按当前回合状态把初始上下文插回合适位置，然后调用 replace_compacted_history 安装新历史。下一次请求基于这个替换结果继续，待接续的用户输入仍需按原角色进入。只在聊天里发一句“请总结以上内容”会多产生一条普通对话，主动压缩则会改变后续请求使用的历史。本地压缩与历史替换

如果自己在 Responses API 上搭 Harness，独立压缩端点接收仍能放进模型窗口的历史项，返回压缩后的输入项序列。调用方用返回序列作为下一次请求的基础，再追加新输入，并继续提供同样的应用指令。遇到不透明的压缩项，原样保留它的结构和顺序。这个接法描述的是 API，后面的 /compact 是在 Codex TUI 里操作。Responses API 的压缩接口

四、一份有用的摘要要保留什么

用第一篇的练习仓库做一次压缩前后的对照。先让 Codex 只改 src/sort-dates.mjs 的排序逻辑，明确公共 API 兼容、禁止新增依赖，并在局部检查后停下。换成自己的项目时，使用实际路径和检查命令。练习仓库的创建步骤

让它把阶段状态写到任务交接文件，例如 .task-notes/sort-dates.md。这是调用方维护的记录，续作时通过路径显式引用。示例中假设局部测试已跑过，完整测试仍待执行。

这比“已经分析并修复了日期问题”更有用，因为它保留了约束、验证范围和未完成动作。

一个常见压缩错误是把状态写得过于肯定。“局部测试通过”被压成“测试通过”，后续代理可能跳过完整验证。另一个错误是把废弃方案留成当前决定，导致任务绕回原路。

接着在 TUI 输入 /compact。压缩完成后先要求 Codex 只读复述当前目标、禁止新增依赖的要求和未运行的检查。对照交接文件和 /diff，确认它区分局部测试与完整测试，再让它运行 node --test。如果复述漏了约束，就引用交接文件，补回最新决定，再续作。长日志也用同样的办法处理，交接里写命令、退出状态、关键信息和日志路径，后续只读需要的片段。CLI 的压缩与差异检查

压缩后为什么还可能被 Hook 撑满

压缩释放的是旧历史占用的空间。根会话压缩完成后，匹配 source: "compact" 的 SessionStart Hook 还能在下一次模型请求前加入 additionalContext，回合中途自动压缩也走这条续作路径。如果脚本每次都把完整交接记录或日志重新注入，压缩刚释放的空间就会被重新占用。频繁工具 Hook 返回长反馈，或者 Stop 每次都用长 reason 请求续作，也会让历史持续增长。这类“上下文爆栈”指的是模型请求超出 token 窗口。Hook 的压缩续作与长输出处理

Codex 默认对单条模型可见 Hook 输出使用约 2,500 token 的裁剪阈值，超出的完整文本会尝试写入临时文件，模型只收到首尾预览和路径。命令处理器可以用 additionalContextLimit 限制自己的 additionalContext。这个阈值按处理器独立计算，工具反馈和续作提示仍用各自的默认裁剪路径，多个 Hook 的输出照样会累加。

在日期排序案例里，可以让 PreCompact 只记录压缩触发类型和任务检查点，PostCompact 只记录完成，实际续作提示则由 SessionStart 的 ^compact$ 分支返回一行交接路径。把这个处理器的 additionalContextLimit 设成小的正数，例如 300。日志留在文件里，确有需要时只读与失败用例相关的片段。若 Stop 用于补跑测试，先检查 stop_hook_active，限制自动续作次数。连续发生压缩时，先缩小 Hook 的输出和匹配范围，再用相同任务验证压缩后的第一步是否回到实际工作。配置、脚本与复测步骤

五、拼接时保留角色、来源与顺序

第 7 章最有帮助的地方，是把 Prompt 展示为不同来源片段的组装结果。

参考版本中，基础指令可以来自显式配置、历史保存的信息或模型默认指令；Skill 的可用目录进入 developer 片段，被选中的 Skill 正文则包装为带名称和路径的 user 片段。这些是参考版本的具体实现，不是所有代理系统必须采用的角色分配。

这是一张组成示意，真实序列需要遵循实现中的插入规则。核心原则是：拼接不能抹掉来源差异。用户授权、项目约定、工具返回的网页内容，各自承担不同角色。外部材料即使写着“忽略之前的要求”，也不应因此升级为运行策略。

工具调用与结果也需要保留标识关联。裁剪时留下结果却丢掉调用，或保留调用却丢掉结果，都可能让模型误解执行状态。恢复中断历史时，应明确记录未知结果，而不能凭一条调用推断操作已经成功。

六、Skill 为什么先给目录，再读取正文

安装的 Skill 越多，把全部正文放进每次请求的成本越高。参考第 7 章采用的思路是渐进加载：先展示名称、描述和路径，让代理知道有什么能力；命中任务需要的 Skill 后，再加载具体步骤。

在目录预算不足时，参考实现会先缩短描述，最小目录行仍放不下时才省略部分条目。若确实是目录太大，支持 skills.max_context_tokens 的版本可以用 codex -c skills.max_context_tokens=4000 做一次对照。这个键只调技能目录的 token 预算，正文还是按任务加载。调整前先确认 4000 相对当前预算是增加还是缩减。技能目录预算配置

想复用日期排序的回归流程，可以在练习仓库中手动创建 .agents/skills/date-sort-check/SKILL.md，团队共享时随仓库提交，个人跨仓库用则放到 $HOME/.agents/skills/date-sort-check/SKILL.md。描述写清什么时候选它，正文只放命中后才需要的步骤。Skill 的发现目录和加载方式

从仓库根开新会话，先用 /skills 确认列表里有 date-sort-check，再发送“用 $date-sort-check 检查当前改动”。观察是否执行了正文里的具体命令并报告覆盖情况。显式调用成功后，再用“验证跨时区的日期排序回归”测试隐式匹配。显式可用而隐式经常漏选时，改 description 的触发场景。列表里都找不到时，先查 SKILL.md 路径、头部字段和当前目录，再查技能是否被配置禁用。若正文已执行到命令却被拒绝，去查第三篇的工具权限。

七、怎样检查压缩与拼接是否有效

如果在自己的 Harness 中实现这套机制，可以用下面的流程做设计参照：

检验重点不只是 token 降了多少。更关键的是：用户最新纠正是否保留，未完成动作是否仍能识别，摘要中的证据能否定位，下一步是否重复已经做过的副作用操作。

例如，在“修改文件完成、测试尚未运行”时触发一次压缩，再继续任务，观察代理是否会先运行测试，是否还记得禁止新增依赖。这类固定恢复任务，比只看摘要读起来是否流畅，更能判断压缩是否支持实际工作。

上下文越长，越需要把任务状态、来源和证据组织清楚。压缩负责让历史保持可用，拼接负责让当前规则与材料正确进入下一次请求；两者的交接处，往往就是长任务能否稳定继续的关键。
